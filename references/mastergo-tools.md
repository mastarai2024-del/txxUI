# MasterGo 工具路由与异步写入

这里记录曾经使用的工具及决策方法。每次使用先看当前 server 的参数、规则和返回值；版本变更后以实际接口为准，不照抄历史端口、缓存目录或内部请求。

## 路由

| 目的 | 工具路径 | 容易误用的地方 |
|---|---|---|
| 新页面设计 | `design_page` → 当前流程要求的准备 → `submit_page_to_canvas` | 不绕过来源/组件库选择，不把多页合成一次提交 |
| 读取画布 | `get_selection_node`、`get_screenshot` | 读取快照不是导出前端项目，也不授权修改 |
| 局部文本、样式、布局、子结构 | 快照 → `agent_update_node` | 保留未改属性；仅改父容器可按当前说明传空根节点保留子树 |
| 替换图片或图标 | 快照 → `agent_replace_node` | 修改 `img src` 不走普通样式更新；不要无需求重建整个画板 |
| 本地 HTML 全量覆盖已有根节点 | `agent_sync_design` | 必须满足当前当次确认及根节点校验；“在 MasterGo 画图”不等于全量覆盖 |
| 导出前端代码 | 用户明确要求后 `get_frontend_code` | 先确定目标格式；不为了找节点而调用 |
| 非默认字体 | `get_fonts` 后使用返回的精确 family | 只查 name 不代表可用；字体写在实际文字节点，不依赖父级继承 |
| 变量 | 当前变量规则 → 读取 → 更新 → 再读 | 不把“变量已写入”当作页面已经引用 |

生成页的最终提交方式按当次工具规则执行。已有图层快照可能是内联 style，局部修正保留其表达，不为满足新页面的生成格式而顺手重写全部结构。

## 提交代码的转译规则

提交前加载当前流程要求的 `get_guidelines`，不要把旧 HTML 原型原样送进画布。已有原型可作为内容和交互依据；实际页面按当前可转译的静态结构提交。

曾使用的基础规则要求：一个页面一个根节点、纯 HTML、语义化图层名、Tailwind 明确值、Flex 布局、无 margin/Grid/相对单位。长文用有限宽度的 `p`，确定单行的原子文字用 `span`；字号、行高、字重、颜色和对齐完整。容器承担背景、边框和布局。

图标、图片、变量、图表和组件模式各有规则；例如组件库模式可能覆盖自由绘制的图标来源。不要自造未支持的标签、脚本、图表路径或内联 base64。严格还原任务优先保存真实素材和图层，不用关键词占位图冒充原图。

这些约束只在当前工具仍采用该协议时适用。已有快照的内联 style 用于局部修正时应保留，不能为“格式统一”删掉未涉及的属性。

## 设计来源与组件库

- 自由绘制可以严格还原现稿；不是重设计授权。
- 当前文件可能记住上次的设计来源或组件库选择。沿用是工具判断的结果，不能伪造用户确认字段。
- 只有生成流程返回快照准备要求时，才获取相应组件信息，并带工具要求的标记回到原流程。
- 用已确认、有序的库 ID 白名单。不要读取其他项目的 local 库、遍历所有缓存，或凭同名库替换来源。
- 组件集、主组件、变量和普通页面是不同操作。没有需求时不额外抽组件。

## 每次修改前

1. 确认目标属于写入白名单，且快照仍对应当前节点。
2. 保存受影响子树、位置、文字和图片依据。只读来源保持不动。
3. 根据快照构造改动；不靠省略样式删除属性。
4. 只改父容器时保留子树；改内部结构时保留所有应保留的节点。
5. 跨父容器移动后，预计节点 ID、顺序和引用可能变化。回读后更新清单，再定位下一步。

CSS 的 `z-index`、Flex 对齐和子节点书写顺序不一定等价于画布的实际图层顺序。以回读和截图为准。

## 截图新鲜度与文件选择

使用工具返回的精确路径，并核对画板名称、尺寸、关键文字和当前节点结构。目录中可能同时有子节点图片；不取“第一张PNG”作为整页。图与节点不符时先暂停批量导出或文档替换，在当前工具允许范围内重新选择画板、调整导出倍率或从原生画布取图，确认新鲜后继续。

跨页读取时保留文件、页面和图层的完整身份。若工具返回目标页面不匹配，使用该来源的完整定位链接或切换到正确页面；不把工具的部分成功误报为全批完成。记录每个成功路径和失败项，避免重取已经成功的无关项。

学习任务可保存一次只读快照供本地属性清点；正式稿发生变化时，受影响快照、截图和映射一同更新。截图新鲜不等于视觉合格，仍需查看实际内容。

## 区分提交结果

| 返回情况 | 下一步 |
|---|---|
| 明确 rejected / 未进入队列 | 修复原因或等队列释放后，重提这一条；不要重放已受理条目 |
| accepted / 已受理 / 指令已发送 | 记为处理中，先遵守工具的等待或停止要求 |
| 超时、断连、结果未知 | 保存请求目标与时间，等允许读取后查是否已应用；不立刻切换渠道重复修改 |
| 工具称成功 | 仍需当前流程允许的节点回读与截图，才能确认实际效果 |
| 明确要求本轮停止或用户决定 QA | 停在该边界，说明待验收；不通过 sleep、其他读取工具或原生界面绕过 |

记录每条请求的目标、动作、返回状态及最后一次观察。没有完成事件时，只在工具允许的阶段做有界等待和少量观察；等待了若干秒不是完成证据。

## 控制队列

- 新页面逐页生成、逐页提交。
- 局部修改先用小批次确认吞吐，再继续。不同节点共享同一画布队列，并行 Promise 不一定提高速度。
- 依赖顺序要串行：例如先改遮罩，再改上层弹窗，并检查实际堆叠。
- 队列满后先等已受理请求排空。不要把同一请求通过 MCP 和原生界面同时提交。
- 参数校验失败按返回说明纠正；相同操作反复无效时检查能力和实际状态，停止无意义重试。

## 工具要求的生成后检查

曾使用的版本对自由绘制与组件库分别设置生成后门禁：自由绘制提交后要求结束本轮；组件库要求用户选择是否 QA，并绑定具体 review ID；QA 发现问题后还可能要求再次决定是否修复。

这些是版本相关规则。执行时逐字遵守当前返回要求，不沿用旧 review ID，也不把一次局部修复授权套到另一次生成的 QA 上。已有用户明确请求的修改与普通生成后的自动 QA 要分开判断。

## 原生界面补位

MCP 不提供页面树导航、复制实际图层，或已确认局部能力失败时，可使用可用的原生 UI 自动化。先读取该工具文档、当前页面与选区；不要复用历史 AX 编号或固定坐标。

原生操作承担必要的选择、复制和属性修改，仍用适用的回读/截图验收。它不能绕过权限、工具要求的确认或未知状态对账。没有可靠路径时，报告具体缺口。
