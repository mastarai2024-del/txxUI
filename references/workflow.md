# 从需求到 MasterGo 完稿

适用于多状态绘制和按原稿补入口。局部修改不必重走整套流程。新页面生成先遵循 SKILL.md 中的工具路由，再在工具允许的阶段完成以下工作。

## 1. 分清输入分别决定什么

| 输入 | 决定的内容 | 需要核对的地方 |
|---|---|---|
| PRD | 功能、条件、权限、前后结果、验收边界 | 当前修订、被删除或划掉的规则、未决项 |
| 交互原型 | 入口、页面转换、返回路径、状态变化 | 是否只是演示开关；是否能从真实控件进入 |
| 用户指定的最终 UI | 整页还原时决定结构与细节；只学画风时仅决定获准迁移的视觉属性 | 来源身份、作者归属、版本区域、同模块状态与迁移范围 |
| 现有 App 截图 | 当前菜单和控件形态的补充证据 | 平台、分辨率、系统栏；是否被用户指定为本轮基准 |
| 设计规范 / 组件库 | 可复用的 token 和组件状态 | 是否属于当前项目，是否被选中，是否与当前原稿冲突 |

业务与视觉来源冲突时说明具体条目。不能凭“V2”“After”字样就认定最新；以用户当前指定及实际内容为准。没有现成设计系统的新项目，记录缺口和用户允许的新设计范围，不强行寻找不存在的规范。

## 2. 建立页面与状态清单

先把文档里的重复截图合并为状态，不机械地“一张图生成一页”。至少识别：

- 来源页面和触发入口；
- 操作菜单、编辑/选择、确认、结果；
- 取消或返回到哪里；
- 需求中确实存在的失败、空状态、选中/未选中和条件展开。

例如“删除一条内容”可以是：内容列表 → 真实更多入口 → 操作菜单 → 删除确认 → 列表移除及结果提示。是否需要原因、是否可跳过、是否保留原内容由 PRD 决定，不能由 UI 绘制者补造。

给每个状态稳定的序号、用途、来源及目标节点，明确哪些是已有页面副本、哪些是新增状态。所需画板数量由清单决定，不固定为案例中的数量。

## 3. 锁定目的地与来源

按 [画布归属规则](../SKILL.md#画布按任务与-prd-归属) 决定新建或复用。此处“画布设计稿”指承载一项需求各个界面/状态画板的独立 MasterGo 页面；文件、页面与画板按当前界面的实际层级识别。不要把每张手机界面分别建成一个文件。

先用已知的 PRD 链接/标识、任务记录及目标映射核对归属。同一任务、同一需求的续做复用原画布；同一产品下另一份 PRD 的其他需求新建画布。没有可确认的既有归属时，新设计默认新建，不把当前选中页、同名页或历史测试页直接当目标。明确修改现有节点或用户指定目的地时，沿用该目标；只读评审无需建画布。

新画布用“需求名 / 模块名 · UI 设计”等能识别需求的名称；重名时加 PRD 短标识或日期。在已确认的项目设计文件内新建独立页面即可，不因新增需求另建产品文件。若文件尚未确定，利用现有上下文和当前工具能力确认；缺失信息确实影响归属时才澄清，不在无关文件中落稿。

首个 MasterGo 动作仍按入口的 `design_page` 路由，在工具允许的阶段创建或切换目标。提交前记录并确认实际文件、页面名称与标识；把工具接受的精确标识带入生成/提交，工具不支持定位参数时通过原生界面确认当前位置。若工具自动落到其他页面，先纠正目标再写入；无法创建或定位时报告阻塞，保留已完成的需求整理，不向来源页或其他需求画布写入。

在任务记录中保存 PRD → 任务 → 目标文件/页面的映射，以及新建/复用理由，供后续续做判断。画布确认后再登记写入白名单。

来源图层只读。不要在来源页面调整大小、颜色、裁切、文本或实例状态。需要复制时，复制后立即回到目标，确认父容器、画板和新节点；不要使用剪切。

页面、子页面、画板是不同层级。用户说“下面添加子页面”时，确认创建的是所需层级；不要把多张手机画板误当作多个文件，也不要移到未授权分类。

## 4. 建立视觉基线并应用 Taste

已有项目风格档案时先核对当前来源与本次组件锚点，复用未变化的规则；没有档案或用户要求学习设计师时，按 [风格学习方法](style-learning.md) 取样。先读取项目实际规范、目标原稿与相关控件，不只看首页。按入口中的 Taste 流程准备本次所需内容。记录：

- 画板和平台尺寸、状态栏、底部系统区域；
- 页面背景、卡片、按钮、选中态、危险色；
- 字体实际 family、字号、行高、字重、长文本换行；
- 间距、圆角、描边、蒙层、图片裁切；
- 旋转文字、混合模式、完整背景及设备状态等复杂组合。

规范与现有稿不一致时，区分用户明确要求的局部优化与未决设计冲突。前者只作用于获准范围；后者记录后澄清，继续不依赖答案的页面。

视觉基线确定后再构思。现有产品的配色、字体、按钮形态由项目基线决定；Taste 用于判断层级与细节，不把“优化”默认解释为改色或重塑品牌。

## 5. 选择最小改动的绘制方法

- 用户仅要求迁移设计细节：沿用认可的屏内布局和画布编排，替换对应角色参数及真实素材；不复制来源整页坐标。
- 原页面只需补一个更多入口：复制完整原稿到目标，添加入口和新状态。
- 复杂头部已有准确图层：复制完整组并保持顺序、偏移、旋转和裁切，不重新拼近似图。
- 纯新状态：沿用同模块组件及 token，在当前工具流程中生成。
- 图片和图标已有素材：复用实际资产；占位图必须明确是草稿状态，不能当完稿。
- 用户要求独立副本：按 [素材与还原](assets-and-fidelity.md) 处理关联。

每个新页面单独提交。先在获准流程中完成一页的素材和基本布局检查，再扩大到其余同类页面。工具要求提交后停下或确认 QA 时，按该边界交付阶段状态，不擅自继续检查。

## 6. 从局部核对扩展到全组

只读检查请求先列发现；已授权修复时按影响范围处理：

1. 修当前问题，例如缺失的分隔线。
2. 与用户提供的真实样式比较，判断是单一缺线还是整体菜单结构不一致。
3. 同类菜单统一；表单、确认框和结果提示各保留适用的结构。
4. 检查所有复用该区域的状态，尤其同一首页的菜单、纠错、删除和结果页。
5. 回读关键文字与图片，检查未涉及页面。必要时做同尺寸截图比较。

不要将“菜单文字居中”推广为所有表单正文居中；不要把透明成功提示也套成模态遮罩。

## 7. 完稿与交接

满足当前工具允许的验收路径后，按 [布局与验收](layout-and-review.md) 完成视觉检查。目标中存在可编辑画板、实际素材正常、入口和状态对应、底部控件不被裁切，才能说 UI 稿完成。

如任务还包含 HTML 或文档同步，分别执行并记录结果：

- HTML：从真实入口操作，验证取消、返回及保存/删除后可见结果。
- txxprd：接收最终状态映射、截图和规则变化，再按授权范围替换文档图片或附件。
- 任一端未更新时，明确仍是哪一版，不把旧截图和新画板混成一份交付。
