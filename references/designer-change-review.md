# 分析设计师改稿并沉淀经验

用于用户要求“看设计师改了什么、以后照着学、沉淀到技能”的任务。它是只读比较和获准的技能维护，不授权改画布、PRD、原型或发布技能。普通局部改图继续按已有最短路径，不必补做完整历史复盘。

## 锁定真正可比的版本

1. 用用户指定的截图或链接定位文件、页面、版本区域和画板，再找原 AI 交付及其原始节点/导出。当前选中、名称中的日期和版本号只用于定位。若有原稿备份、过程快照、布局重建、组件化等多个阶段，分别标记；不能把某个过程稿当成原交付，也不能把全部净差异都归因给某个人。
2. 按页面用途、状态、内容对象和可见区域配对，列明保留、变化及缺失的状态。不同样例先比较共同结构；少一张画板不等于产品取消了该功能。有一侧证据缺失时，只描述可见稿及缺口，不编造“修改前”。
3. 先读当前节点，再导出一致来源的图片。保存观测时间和本次使用的快照；比较期间发生后续编辑时，固定本轮证据范围或重新读取受影响状态。层名可能沿用母版或旧内容，实际文案看文字内容与实例覆盖值。
4. 同逻辑宽度和倍率观察。画板高度不同时，保持各自自然高度并标注差异，按导航、内容区、底部操作等锚点对照；不要拉伸成同高、计算整页像素相似率，或据此宣布新尺寸已验收。修改前后交付仍遵守[配对要求](layout-and-review.md#修改前后配对)。

历史复盘无需启动与比较无关的模拟 APP；结论仅限所读设计版本。若任务同时涉及当前页面或真实入口，再按[运行页面基线](app-baseline.md)补充相关核验。

## 从“哪里变了”解释到“以后怎么做”

每项先记录可验证的差异，再解释它影响了什么，最后给出有边界的做法。设计意图是分析者的解释，除非有设计师本人说明，不写成其原话或已测量的用户收益。

| 观察次序 | 具体比较 | 可执行的沉淀方向 |
|---|---|---|
| 信息与容器 | 哪些内容同属一组；面板包住多少内容；空白属于页面还是卡片；默认、展开、只读是否换了结构 | 先按语义组织组与子组，按内容计算面板高度；不靠一整页白底、逐行描边或无信息空位补结构 |
| 排版与密度 | 正文、时间、帮助、状态、按钮各自字号/行高；固定元素与弹性内容；时间到正文是否浪费宽度 | 密度通过减少重复信息和无效间距取得，必要时给文字更大空间；不能只追求首屏多几行 |
| 操作关系 | 选择、展开、备注、同意与提交是否各自清楚；状态摘要在哪个锚点；主次操作如何分层 | 选择态、展开态、有备注、编辑/只读分别核对，按 PRD 决定是否联动；不从一个组合图推导自动勾选或新增保存动作 |
| 状态和资产 | 提示文字、图标、颜色是否表达同一结果；系统图标、结果图和字符替代物是否变化 | 复用真实资产及可读状态文字；只继承状态色的语义，不把示例色值、装饰或 Unicode 符号变成通则 |
| 原生结构 | 容器是否真正使用自动布局；文字是否可编辑；实例是否引用主组件；覆盖值是否正确 | 继承已有组件与布局关系；读实际生效的属性，自动布局未开启时，存储的 padding/gap 不能直接算成真实间距 |

同时记录正确的保留项，说明哪些问题仍未解决。字体 family、已确认文案、选择/上传单位、权限和业务状态不由视觉推断替代；既定字体规则不因某份稿使用另一个 family 自动改变。画板尺寸混用、状态文案冲突、漏状态、过浅颜色或导出差异都先作为疑点，不能包装成设计偏好。

## 写入技能的分层

- **通用方法**放在现有流程、设计师比较或布局章节，优先合并同义规则。主入口只增加必要路由，不把完整报告塞入 SKILL.md。
- **模块画像**记录观察日期、组件角色、实际前后变化及适用范围。例如[巴布数据上传案例](babu-data-upload-designer.md)；其他模块重新取样，不照抄尺寸、色值或固定状态数量。
- **项目证据**保留原始截图、节点、私有链接、版本树和详细差异报告，留在项目私有目录。技能只保留脱敏方法与画像。
- **未证实项**留在报告，不提升为强制规则。若组件库是在比较后整理或来源不明，只写“当前已有、后续可复用”；不擅称设计师亲自创建，也不要求所有小改都建组件库。

维护前比较当前技能及实际入口、备份、保留并行变化；维护后检查引用、现有约束和可执行性。用脱敏情景检查：缺少一侧时不虚构差异；尺寸不同不拉伸；已有组件优先复用而非自动抽库；冲突状态不固化；只读任务不外溢到设计写入。结构校验和纸面走查不冒充独立模型或真实应用验收。
